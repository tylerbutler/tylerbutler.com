I've been working on a project for the past few months called [beryl][]. attempts to bring a real-time channels abstraction -- rooms and topics -- to [Gleam][]. If those words mean anything to you, then this will sound familiar. I want to make it easier to build real-time applications, web applications specifically, in Gleam.

I'm fairly new to Gleam, and this is the first big project I've built with it.

I'm also using LLMs a lot. So if that upsets you or offends your sensibilities, now you know.

## Starting from Phoenix

When I started this project, I used [Phoenix Channels][] as design inspiration. Phoenix Channels is built in Elixir. It's in the BEAM ecosystem, but it's built in the Elixir language, and therefore has some different programming models and styles that make sense in the Elixir world but don't necessarily make sense in Gleam.

I don't know Elixir, so I used Phoenix more for design inspiration than for code inspiration. But in the end it doesn't really matter, because a lot of the code stems from the design.

I talked about the overall design and experience of that initial version here:

I had what I thought was a fairly nice Gleam API. There were some type-safety problems with it, most notably type erasure,
but I felt I had it controlled pretty well and had limited the risk. If you're curious, you can use [beryl v0.0](https://github.com/tylerbutler/beryl/releases/tag/v0.0), which
used a heterogeneous registry of sockets/connections.

## Feedback

When I asked for feedback from folks on the Gleam Discord, the number one piece of feedback -- or the most important, I felt -- was that it seemed like I'd be better served by leaning into the language's strengths, and that a heterogeneous registry -- well, that's not Gleam. Gleam doesn't have that. So I was inventing things that don't necessarily make sense in the language.

They were very polite, but also very clear that this just doesn't feel very Gleam-like. It feels too Elixir-y, or too
Phoenix-y, or it just doesn't feel familiar to Gleam developers.

So I took that feedback to heart, and I went back to the drawing board.

## I still don't fully get it

Starting fresh meant going back to a lot of things that I still don't understand fully, that are very new to me, that I'm learning as I go. Specifically the Elm model -- model, view, update, where everything goes through one big update function.

It's one of those architectures that I sort of understand from the outside, and sort of understand why it would be good. But then when I actually see the code that implements the design, I find it really hard to read and hard to reason about.

Part of that is my brain. Part of it is other people's brains, too, because other people also struggle with this. That
doesn't mean the model isn't worth learning, and it doesn't mean the model is bad. It just means that I'm not quite
clear on the model myself. So I'm trying to build something using it, but I'm also trying to learn it and understand it as I
go.

## The connection

I took a harder look back at [Lustre][], which implements the Elm Architecture. Further research revealed that Gleam's [OTP actor model][] is very similar -- it's the same basic architecture of state transitions.

So I started to realize that there was an opportunity to take that state transition inspiration and use that model against socket state.

## MVU, but sockets?

What if we took the Elm Architecture of state transitions and applied it to socket state? That's the question the new design is built around, and it turns out the model works pretty well. Lustre and OTP actors already follow the same four steps: create some state, define the typed messages that can arrive, handle one message against the current state, return the next state plus whatever should happen next. Only that last step differs. Lustre renders a view. An actor continues or stops.

beryl returns _effects_.

| Role       | Lustre        | OTP actor      | beryl              |
| ---------- | ------------- | -------------- | ------------------ |
| state      | model         | actor state    | one model per socket |
| input      | `Message`     | mailbox message | `socket.Input(Message)` |
| transition | `update`      | `on_message`   | `update`           |
| next step  | model + effect | `actor.Next`  | `socket.Next(model, effects)` |

There's no `view`, which changes how you think about output. Changing the model doesn't send anything over the wire. A frame goes out _only when an effect asks for one_ -- accept this join, reply to this client, broadcast to this topic, update presence, close a topic. Output is an explicit, ordered list, so the model is free to hold things that never leave the server.

The other difference from a frontend is that `init` runs once per connected socket, not once per application. Every socket is its own actor with its own model. Shared state -- the poll totals everyone in a room needs to agree on -- lives in an actor your application owns, and each socket talks to it. Per-socket state and shared domain state stay apart.

## Two APIs

Both layers use the same loop. Which one you use depends on how much routing you want to handle yourself.

**[Raw dispatch][]** is the core. You give beryl an `init` and an `update`, and every event on a socket arrives at your
`update` as a single `socket.Input` value: joins, client messages, binary frames, close events, and your own typed
server messages. You do the routing for all of it. You return `socket.Next(model, effects)` or `socket.Stop(reason)`. It's the clearest place to see the whole loop, which is why the walkthrough starts there.

**[Channels][]** sit on top and do the routing for you. A channel is a topic pattern plus a typed `join` callback that either rejects the join or accepts it with private state and a few callbacks -- `on_message`, `on_info`, `on_terminate`. You register a list of handlers, patterns match in registration order, and each joined topic gets its own instance and its own state, pruned automatically when the topic closes.

The part I'm happiest with is that channel state is typed all the way through. Phoenix keeps per-channel state in `socket.assigns`, a map of atoms to untyped terms. A beryl channel keeps a value of its own type, known to the compiler, and unrelated channels can still live in the same handler list. Nothing gets stuffed through `Dynamic`. The same is true of server-side messages: `notify` delivers your own type to the right join's `on_info`, and a sender only ever addresses the join that produced it.

Actions work the same way effects do, with one useful constraint -- an action can only touch its own channel's topic.
Cross-topic work has to go through an explicit API. That felt restrictive when I wrote it but after more thought, I came
around to it.

If you have more than one topic namespace on a socket, the channel layer is what you want. If you want one topic family and total control, raw dispatch is right there underneath, and moving between them doesn't change the wire protocol.

## Going deeper

I've skimmed a lot here. The [tutorial][] on the docs site builds a live poll end to end -- the raw loop
first, then the same poll moved onto channels, then typed server messages, presence, and supervision. That's the deep
dive for anything I described that you want to see in more detail.

The resulting API is pretty interesting, and more to the point, it feels a lot more like Gleam than what I had before, which was the whole idea.
